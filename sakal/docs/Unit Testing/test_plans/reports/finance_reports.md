### Real bug found + fixed — Day Book Register & Cheque Register both returned a raw 404 on Run Report

**Root cause (confirmed via direct network-request tracing, not guessed from the symptom alone)**: the generic reporting engine's `report_repository.dart` (line ~300-301) builds RPC date-range parameters as `p_${filter.paramTarget}_from`/`p_${filter.paramTarget}_to`. Migration 166 (which added both reports) set each report's `date_range` filter's `param_target` to `'trans_date'` — but `fn_day_book_totals`/`fn_day_book_group_summary`/`fn_cheque_register_totals` (also from migration 166) all declared their own date parameters as `p_date_from`/`p_date_to`, not `p_trans_date_from`/`p_trans_date_to`. PostgREST returns a plain HTTP 404 (not a 400 or a clear error) when an RPC call's named parameters don't match any function overload — this is deliberately obscure PostgREST behavior, already documented in project memory (`feedback_supabase_fn_deployment.md`), which was checked and ruled out first (EXECUTE privilege confirmed fine, `NOTIFY pgrst, 'reload schema'` made no difference — the mismatch was genuinely in the request itself, visible directly in the captured request URL).

**Two different fixes were needed, not one** — this is the real lesson, caught by re-verifying live immediately after the first deploy rather than assuming it worked:
- **Day Book Register** has a `ric_report_group_levels` row (`fn_day_book_group_summary` as its level-1 group summary source) — its MAIN grid query, not just the footer totals, goes through this RPC. Fix: migration 233 corrected the filter's own `param_target` from `'trans_date'` to `'date'`, matching the RPC's real parameter names (same convention already correctly used by `ACCOUNT_LEDGER`/`CASH_FLOW_*`/`PROFIT_LOSS_*`/`FINANCIAL_RATIO_ANALYSIS`).
- **Cheque Register** has NO group-level config — its main grid queries the `v_cheque_register` VIEW directly via PostgREST column filters, where `param_target` must match the VIEW's own column name (`trans_date`, confirmed via `information_schema`). Applying migration 233's same fix to this report broke its previously-working main query (HTTP 400, "date" isn't a column on that view) — caught immediately via the same live re-verification discipline. Migration 234 reverted this report's filter back to `'trans_date'` and instead renamed `fn_cheque_register_totals`'s own IN parameters (`p_date_from`/`p_date_to` → `p_trans_date_from`/`p_trans_date_to`, via `DROP FUNCTION` + `CREATE` since Postgres disallows renaming an IN parameter through `CREATE OR REPLACE` alone) to match what this report's filter config actually sends.

Both fixes deployed and re-verified live via browser screenshot + network trace before being marked Passed above. Full detail, including the "why one report needed the opposite fix from the other" reasoning, is in migration files `233_day_book_cheque_register_date_param_fix.sql` and `234_cheque_register_fix_correction.sql`.
